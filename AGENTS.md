# Working in this repository as an agent

[DEVELOPMENT.md](DEVELOPMENT.md) says how to set up, check and test. Before you finish a task, show that it works: [Showing a change works](DEVELOPMENT.md#showing-a-change-works) says how to screenshot a component's story or the desktop app, headless, and where the shots go.

Before UI, copy or site work, read [DESIGN.md](DESIGN.md). Before work on the window or the runtime, read [The UI is instant](docs/decisions/foundations.md#the-ui-is-instant): every press shows its result at once, optimistically, and nothing heavy runs on a thread that answers the person. Two lint rules check part of it (`althar/press-at-once`, `althar/off-the-thread`), and review checks the rest.

Run only what is cheap and fast: the checks and unit tests of the packages you changed and of those that build on them, with few workers (Vitest's `--maxWorkers=1`), and an end-to-end spec only when your change is what it covers (`bun run test:e2e e2e/that.spec.ts`, one worker already). Don't run the full suites, coverage or the desktop app's whole end-to-end run: the pull request runs the checks and the unit tests your change reaches, and once it's ready the coverage gates of the packages it reaches and the end-to-end run when it reaches the app, the merge queue runs what your change and those landing beside it could break together, and everything, Windows' tests, coverage and packaging too, runs after merge on main ([Changes and CI](DEVELOPMENT.md#changes-and-ci)). Althar tells you when one fails. Other agents share this computer.

Where a change goes, so it doesn't rebuild the shapes [the refactor](docs/plans/refactor.md) took apart:

- **A new call to the API** is its schemas and RPC in its area's module of the contract, `packages/contracts/src/api/<area>.ts`, and its handler in the runtime's, `packages/runtime/src/api/<area>.ts`. Neither `Api.ts` grows: lint refuses a call defined or a handler written there (`althar/calls-in-areas`). Run `bun run snapshot` in `packages/contracts` and review the diff of `api.schema.json`: it is the change to the wire ([Adding a call](packages/contracts/ARCHITECTURE.md#adding-a-call)). A value a newer home may send that an older client doesn't know is read through the contract's open unions ([Clients of another version](docs/decisions/foundations.md#clients-of-another-version)).
- **A new runtime module** takes a row in the layer table (`packages/runtime/layers.js`) and imports only down it; lint refuses an import up, a value import cycle and a re-export outside an `index.ts` ([Where a file goes](packages/runtime/ARCHITECTURE.md#where-a-file-goes)). A file split for its length goes by what each part does, never into stubs that pass names on.
- **A migration** is one new file in `packages/persistence-sqlite/src/migrations`, and `schema.sql` regenerated. Once main has it, it never changes ([its README](packages/persistence-sqlite/README.md)).
- **Counts that may only fall** are in `.github/measures.json`: lower one when your change does (`python3 .github/scripts/measures.py --update`), never raise it.

Open your pull request as a draft while you're still pushing to it, and mark it ready for review (`gh pr ready`) when it's done: a draft runs only its checks and unit tests, and each push to a ready one runs the end-to-end runs and the stress run of its changed tests too.

After every push, monitor CI on the pull request's latest head through completion. Inspect all GitHub check runs and commit statuses, including CodeQL and other external checks, as well as Actions workflow runs. Inspect failures, fix their causes within the task's scope, push the fixes, and monitor the new head again. Do not finish the task or report it complete while relevant checks are pending or failing. Passing local tests or some CI jobs is not enough. If a failure cannot be resolved within the authorized scope, report the specific blocker instead of claiming completion.
