# A readout of the Mac's load

A prototype to pick a direction from: how hard the Mac is working while agents work, small enough to ignore. Fixtures only; nothing reads real numbers yet. Each direction has the same states (idle, one agent, several, near max), its detail, light and dark, a **Live** story with a made-up loop of a build and a test suite, and its off state. Each is shown here busy, with four tasks running, on paper and on the dark stand-in.

What every direction shares:

- **Ink for the Mac, cobalt for the agents' part.** Cobalt already means the work Althar runs, so the readout rhymes with the running dot beside it. No new colour: under strain the ink goes to full strength and a word says why ("Slowed by heat", "Memory is tight"). Red stays for failures, violet for what waits on you.
- **Pressure and heat, not only percentages.** A Mac keeps memory full of cache on purpose, so "90% used" is not a problem by itself; macOS's memory pressure is. Heat matters because from "serious" the Mac slows itself, and every task with it.
- **Steps, not a live number.** A meter in fifths changes only when the load moves by a fifth. With reduced motion nothing eases between values, and the live stories sample a third as often.
- **Off until turned on**, in Settings, with "Only while work runs" under it (<a href="./?path=/story/prototypes-system-usage-turning-it-on-and-off--in-settings" target="_top">Turning it on and off</a>). Off, nothing is left in its place.
- The dark stories use a stand-in that maps the tokens, since Althar has no dark theme yet. The readouts use tokens only, so a real theme would carry them.

Put **A's meter** in the bar, and make a click on it open **D's peek** (<a href="./?path=/story/prototypes-system-usage-e-recommended--open" target="_top">E. Recommended</a>). The meter answers "how hard is the Mac working?" without being asked, and its steps hold still. The peek answers "which task is it?", which only Althar can say, and holds B's trace and the off switch where they are asked for. Drop A's swap to figures (the peek has the numbers), B at rest (history belongs in the detail, not the corner of your eye), and C for now (it crowds the context ring, and is missing from the board, where several tasks' load adds up). If the bar must stay smaller still, D's gauge can take the meter's place with the same peek.

## Reading real numbers later

Not built. One sampler in Electron main, running only while a window shows the readout, sends the renderer formatted numbers every 2 to 3 seconds:

- **CPU:** deltas of `os.cpus()` times between samples (busy over total, across cores). Cheap, and no process spawned. `os.loadavg()` is a one-minute average of runnable threads: too slow, and not a percentage.
- **Memory:** `process.getSystemMemoryInfo()` for used and total. For pressure, macOS's own level (`sysctl kern.memorystatus_vm_pressure_level`: normal, warn, critical), which Node has no API for.
- **Heat:** `powerMonitor.getCurrentThermalState()` and its `thermal-state-change` event, on macOS. Event-driven, so free.
- **Althar itself:** `app.getAppMetrics()` covers the app's own processes (main, windows, GPU), not the agents.
- **Each task:** the runtime already lists `ps -A -o pid=,ppid=,time=` to sum each agent's process tree (`packages/runtime/src/processTree.ts`). Adding `rss=` to the same listing, and taking CPU-time deltas between samples, gives every task's CPU and memory from one `ps` per sample.

The sampling cost is mostly that `ps`: a process spawned and every process listed, some tens of milliseconds every few seconds. One listing for all tasks, only while the readout shows, and slower while the window is hidden, keeps the readout from being what loads the Mac.
