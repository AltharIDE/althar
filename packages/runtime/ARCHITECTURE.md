# @althar/runtime — Architecture

The runtime of [docs/architecture/02](../../docs/architecture/02-desktop-runtime.md): the composition root that owns the store, agent sessions and their processes. The repository's [ARCHITECTURE.md](../../ARCHITECTURE.md) sets the general engineering target.

- **Owner:** Repository maintainers
- **Consumers:** the desktop app's utility process (`apps/desktop`), over the API; the command-line client (`apps/cli`), in its own process.
- **Dependency direction:** depends on `@althar/contracts`, `@althar/domain`, `@althar/persistence-sqlite`, `@althar/provider-adapters` and `effect`. It imports nothing from Electron.

## Principles

- **Accepted, then acted on.** Input is committed to the thread's queue, with its user message, before anything is sent; a turn is recorded as delivered, with the prompt it sends, before the prompt goes out. After a crash, a delivered turn may have acted, so it is marked uncertain, never repeated. A prompt the agent refuses puts its input back in the queue.
- **Every session starts from a brief** (ADR-005), the first on a task too: the task, its worktree and base, the plan, what changed since the start and what isn't committed, and the thread so far. A switch starts the new agent first and stops the old one only once the new one is ready, so a switch that fails leaves the old agent working; the brief is written after the old one stops. Start, switch and stop on one thread run one at a time, and the store keeps one live session per thread.
- **No I/O inside a transaction.** Git and agents run between transactions. A task's worktree is added after the task is committed, and its workspace marked ready or failed after git finishes.
- **The runtime's own git** runs with the repository's hooks off, fetches before a task starts so it starts from the default branch as origin has it, picks a free branch and folder when the planned ones exist, and records remote URLs without the credentials they may carry. The default branch is origin's, or the usual name, never whatever the person has checked out.
- **Every change of state is recorded with its revision.** Rows move on with `change`, which bumps the revision; facts go to the record with `fact`. Session states move only along the lifecycle in `@althar/domain`.
- **Thread items are what the person reads.** An agent's message is one item, placed when its first chunk arrives and written every couple of seconds or kilobytes as it grows; a tool call is one item, updated as it runs. Updates reach clients through the change feed without adding facts to the record. A failure to record one event doesn't stop the runtime reading the rest of the turn.
- **The record keeps a tool call's command and paths, not what it writes or what came back** (07: no file contents, so no secrets, in the store). A thread item and a permission request keep the command (up to 4,000 characters), the paths, and which files a patch touches, and name what they left out. The rules decide on the whole input, in memory.
- **A failed command keeps what it printed, in short, with its status** (`diagnostics.ts`, 07). As it ends failed, its item keeps an excerpt, before anything the agent says next is recorded: what it printed (or, where the agent sent none of it as output, the `stdout`, `stderr`, `output`, `error` and `message` of what came back, never a whole object), what the tool said of the failure, and its exit code, its terminal styling gone and what looks like a credential taken out (looked for in its first 16 KB and last 48 KB, in time that grows with its length), then cut to its first 1,000 and last 3,000 characters. So a restart before the agent says anything of it loses nothing, and the brief of an agent that takes over has it under the tool call's line, as what the tool reported. A command that reads files or the environment (`cat`, `grep`, `env` and the like, not one a pipe feeds) keeps none, nor does one that succeeded.
- **What agents hand back goes to the artifact store, not the record** (ADR-020). A picture (up to 20 MB, a kind the window draws, told by its bytes) and a command's output once it ends (its last 256 KB, cut at a line, counting what went) are files named by their SHA-256 under the profile's `artifacts` folder, written aside and renamed into place before their rows (`artifacts`, `artifact_links`) are committed; both are marked as possibly holding secrets. An item keeps what a picture is and its digest, or why it wasn't kept, and how much a command printed. A file an agent wrote whole or pointed at is kept by its path; a picture a link points at is read only from inside the folders the agent works in. A command's output runs in memory and goes to watching clients as its last lines (`Output`), at most every 50 ms, and a client that opens mid-command reads it so far (`ReadOutput`); a turn that ends keeps what its commands printed so far, and nothing heard after a command ended changes what it kept. Without an `artifactsRoot`, nothing is kept, and the item says so.
- **Images the person sends are artifacts too.** `Send` and `SwitchAgent` take images as bytes or, for one kept already, a digest; each is checked by its bytes (`sentImages.ts`) and written to the store before the command runs, which names them by digest in its payload, never its bytes, and records them in order in `user_input_images`. The message's item carries them as an agent's pictures are carried. Every turn that delivers the input sends them from the store as image blocks after its words, after a restart too; to an agent that doesn't say it takes images (`AgentInfo.images`), none go: the prompt says they were there, and a notice in the thread says they weren't passed on. Whether each agent takes images is in `GetModels`, from asking it or its latest session. Without an `artifactsRoot` none can be sent, and `Send` says so.
- **A project's vocabulary is read from git when asked, never kept.** Its tracked files' names with parts, and the camelCase, PascalCase and snake_case names in the 300 most recently changed source files (the first 256 KB of each, binaries and links left out), counted and said most used first, at most 3,000 (`vocabulary.ts`, ADR-017).
- **A task's change is read from git when it is asked for, never stored.** The list of files runs from where the task's branch meets its default branch (so upstream work merged in isn't the task's) to its worktree as it stands, committed or not, each saying how it changed, how much, and whether part of it isn't committed yet. A new file nobody has added is read as git would add it: a link as its target, never what it points at, and nothing that isn't a file or a link; only the first 50 are read to count their lines. A file's diff is its hunks, with the stretch of a changed line that differs marked, cut short past 4,000 lines; only a file on that list can be asked for, by its literal path (`diffs.ts`).
- **What an agent left running is kept with its session, in memory** (`leftRunning.ts`, ADR-022): a command it sent to the background, by its tool call's command, where it answers once its output says (read every half second for two minutes), and how it ended if it did by itself, until cleared. Stopped, it goes. It is on the session's summary and goes to watching clients whole each time it changes; nothing of it is in the store, since nothing of it outlives the session.
- **Althar sets up a task's worktree before its lead starts** (`Setups.ts`, ADR-023): the setup its repository keeps (`run_setup`), else the install its lockfile names, for its own packages or its workspaces' (`installIn`: run as it is, where a run's `setupIn` skips it once `node_modules` is there), as the worktree is made (`Projects.createTask` begins it) and again for one a reopened task puts back, forgotten as soon as it is back. It runs in the person's login shell, interactive, recorded as purpose `setup`, for ten minutes at most (`setups.within`), one at a time per worktree. How it went is kept on the workspace (`workspaces.setup`, JSON; null until it ran), so it runs once. A `setup` item in the task's thread follows it; at start, items an earlier launch left open are marked stopped. A lead's first turn waits for it in `Sessions.deliveries`, outside the turn's permit, so stopping isn't held up, and its brief says how it went (`Setups.told`).
- **Althar runs the project itself, with no agent** (`Launches.ts`, ADR-023): the command each repository keeps (`run_command`, `run_setup`), or one worked out from it, in a task's worktree or a copy of the default branch under `.run`, made fresh each time, beside the coordinator's. The process is recorded as purpose `run` and stopped as an agent's is; what it prints is read for where it answers. Runs are kept in memory, go to watching clients as `Launches`, and are on the coordinator's snapshot (every run in the project) and a task's (its own), with the command running would run. Each run posts a `run` item in the thread it was asked for in and changes it as the run gets its address and ends; at start, cards an earlier launch left open are marked stopped. Agents keep the command with `set_run_command`; the coordinator starts a run with `run_project`.
- **A project runs many things** (`Launches.ts`, ADR-044): its `runnables`, a list in the person's order, the first its default, each in one of its repositories; one with no command is that repository's own way, above, and a repository bound gets its own (`Projects.ts`). Snapshots carry them as run here (`runnables`), and a run says which it runs. One of each runs in a place; runs of the default branch share their repository's copy, made fresh only where nothing of it runs there. The person keeps, drops and orders them through the API, and picks from the scripts in the project's package.json files (`runCommand.ts`, `scriptsIn`); agents keep them with `keep_run`, and `run_project` runs one by name.
- **Permission decisions are recorded before they are sent,** with the option the adapter will send. A failed decision is a rejection. A permission waiting on the person is withdrawn when the turn is cancelled or the agent goes; an agent's question only when its turn is cancelled, as it outlives its session (ADR-021).
- **Processes are owned.** A process is recorded as launching before it is spawned, then with its pid, OS start time and environment digest. Stopping a session ends its turn first, then its process group, and records both. Reconciliation stops an earlier launch's process group when its leader is the process recorded (pid and OS start time both match), or when the leader has gone but the group lives on, since a pid isn't reused while its group exists. What an agent left running, such as a dev server, runs in a process group of its own, so closing its session asks the agent to stop each one first (ADR-022). A worktree a crash interrupted is marked ready or failed.
- **A project is the folder it was opened at** (`Projects.ts`, 01): a repository, a folder inside one (the binding's `folder`), or the repositories directly inside it, as many as the person kept. `project_folders` remembers each device's folder, so opening it again finds the project; one opened before folders were kept is found by its repository's root. A project made on purpose, named first in its own tab, comes with the id the window made for it (its mark is drawn from it as it is named) and is new even where its first folder is another project's already; that folder stays the other project's to find.
- **A plain task's worktree has no branch until its lead writes** (`firstWrite.ts`, ADR-035). What the coordinator starts with `start_task` is made detached at its starting commit (`Projects.createTask`, `plain`), set up as any, with `.althar/scratch`, whose own `.gitignore` ignores everything in it; its branch's name is planned in `workspaces.branch`, and `workspaces.branched_at` stays null. As a turn of its lead ends (`Runs.watch`) and as it calls `finish_step`, new commits or changes not committed that aren't evidence make Althar switch each of its worktrees to a new branch there (`git switch -c`), under `Changes.exclusive`, so never beside publishing; it records `workspace.branched` with `from: null`, adds a notice to the thread, reads the card and the search row again, and the coordinator's news says so. Until then the task has no branch on its screens, no size, nothing to merge, push or publish (`gitOf` leaves its worktrees out, and so do publishing, merging here and pushing), its run ends without publishing, and its lead's report needs no `built`. A task's kind follows its branch (`kinds.ts`): with one, a change; without, plain. Reopened with its folder gone, it is put back with no branch where it started.
- **A task has a worktree per repository it changes** (`task_repository_requirements`, `workspaces`), side by side in its folder; with several, a task must name them (`RepositoriesNeeded`). Its lead starts in the one worktree (or the binding's folder in it), or in the task's folder; the rules see every worktree and default branch. Steps, review copies, publishing, pushing and the task's files go repository by repository; a file is named under its repository's slug where there are several, and an action on a pull request names it by its address.
- **The profile, worktrees and database are where they were** (`locations.ts`): Althar's folders, unless told otherwise, or the ones it left as Charrette where only those are there, used in place because what the profile holds names paths inside them.
- **One runtime per profile.** The store holds the database in exclusive locking mode, so a second runtime on the same profile fails to open it (`DatabaseInUse`) instead of reconciling live sessions away.
- **Nothing starts on a store an update couldn't migrate.** Given the profile's `backups` folder (`backupsIn`), the store copies itself there before any pending migration runs. A copy that can't be made, a migration that fails, or migrations that leave rows pointing at nothing fail the runtime's composition (`BackupFailed`, `MigrationFailed`, `ForeignKeyViolations`, each naming the copy), so no launch is recorded and nothing is reconciled; the client says what happened. `extraMigrations` lets a test add one that fails.
- **Screens read git once a worktree, and keep the rest** (`Queries.ts`). Read again with nothing changed, a screen costs its queries and one git process for each worktree it shows from git: a look, the commits of its head and of the refs it is read against from one `cat-file`, with its index file's stamp. What follows from commits alone (where the branch meets its default branch and how many commits it has since, whether it is merged here, what isn't pushed) is kept by those commits, so it is never stale. The files a task changed are kept while its head, its index and the lead's tool calls are as they were: an edit nobody staged, by hand or by something left running, shows at the next commit, stage or tool call of the lead's. Nothing that acts goes by what is kept; merging and pushing check the head the person saw in git again. What is kept of a task goes when it leaves the screens: the board lets go of what it no longer shows of its project, the home of every task that isn't open. A screen reads its tasks eight at a time, and a task's worktrees, and the git commands each needs that don't wait on one another, at the same time; what the store says comes first, git after.
- **The computer's load is read only when asked** (`MachineLoad.ts`, ADR-029): at most once every 2.5 seconds however many windows ask, the rest answered from the last reading, and never while none asks. What used how much is worked out between two readings, so a first, or one after a gap, waits half a second for a second. Althar's work is each agent process this launch started that runs, as the store records it, and each run still running, with everything they started, each process counted once; a task's lead, steps and runs are the task's. The last two minutes of readings are kept in memory for the trace.
- **Clients read, then watch.** A query returns a projection shaped for a screen, with the change-feed cursor it read at, taken before its rows. `Watch` says which record changed after a cursor, with the thread it belongs to, what an agent is still saying and what a command has printed so far, at most every 50 ms, how full the context of the agent on a thread is, as it says (ACP's usage updates, kept on the running session in memory, and on its summary while it runs), and what it left running (`Background`, whole each time); a client reads again what shows it. The feed is read when the ledger says it grew, and once a second as a fallback, so a watch is quick when something happens and idle when nothing does.
- **A client's command ids are the commands' ids.** Commands with receipts in the store (opening a project, creating a task, sending, answering) answer a retry from the receipt, even after the thing they did has moved on. Session commands, which start and stop processes outside any transaction, are answered from memory for the launch.
- **Errors reach a client in words.** A failure goes out as `ApiError`, with the runtime's error tag as its reason and a sentence from `words.ts`; anything the person can't put right also goes to the log with its whole cause, and is reported by the call's name (`Failures`).
- **A failure is kept to what it belongs to** ([ADR-047](../../docs/decisions/047-failures-kept-where-they-belong-and-reported-at-the-edge.md)). Where a call or a loop covers independent things, `contained` (`Failures.ts`) puts a stand-in in the place of one that failed, logs it and reports it: in `Status`, an account whose check failed is `unknown`, and an agent whose own check failed carries a `problem`; the Connect guide offers no CLI sign-in for an instance whose CLI didn't answer; a coordinator's delivery and a round of listening to pull requests that fail leave their loop going. The plans' countdown and the usage-limit holds go on past an item they can't start or read: one that fails waits a while before it is tried again, longer each time (`backoff`), and a loop whose round fails whole starts again a moment after (`keptGoing`). Conflict rounds left under way at launch are settled each on its own, a repository whose git fails being that round's reason; one waiting round that can't be read is left out of those that wait; and the lead's read of a task's pull requests says of one it can't read why, and reads the rest. `Failures` says each one, and each call's and each lost agent's, to whoever listens: the desktop app's main process, which sends them as handled crash reports. With nobody listening, as in the CLI, they are only logged.
- **The log is quiet, and by ids.** Besides warnings and errors, the runtime logs each agent's start (its pid and adapter) and stop, and each turn's start and end, at info, annotated with the turn, thread, session and agent ids, how it ended and its error class: never the prompt or what was said. Where it goes is the host's (Effect's loggers): the app keeps it in `runtime.log`, the command-line client shows only warnings. What each agent writes to stderr goes to `agentStderr`, where the host gives one.
- **Sign-in is checked at most once a minute,** unless a client asks again: each check starts the agent's own status command.
- **An agent's models are its own** (03). What it offers are the selects in its session's settings (the `model` and `thought_level` categories), in its own ids and names. Each model has effort levels of its own, and some none, and an agent says them only for the model a session is on. Until it is asked, the latest session it had says, for the model it was on; what it is on is what that session was last set to. Each agent that isn't signed out is asked once a launch, in the background: it starts in an empty folder in its read-only mode, its settings are read, it is put on each model in turn to read that model's levels and the one it starts at, put back on the first, and it stops. Its process is recorded like any agent's (purpose `probe`, with no session), and asking runs in the runtime's scope, so a shutdown or a crash leaves nothing running unknown.
- **A model's default effort is the person's, kept for the profile** (`model_preferences`). Effort is set as a session starts, from a plan's step or the person's pick, and changed within it like the model. A step's effort is the coordinator's where it names one (`propose_plan`, `start_task`), checked against the levels its model offers the way the step goes, or the person's from the plan's card; it shows there as the person's own would, and a change made there keeps it. The task's card says its lead's effort beside its model: what its session is on, or the plan's until that session has said. A session that starts without an effort of its own, however it starts (the person, a plan, its countdown, a switch), starts at the person's default for the model it is on, or else at the model's own: the level the agent's entry names for it (`ownEffort`) where the agent would otherwise put a session on a model's first level, as OpenCode does. Put on another model, a session keeps its effort where that model offers it, and otherwise goes the same way. An effort the model doesn't offer leaves it at the next of these, or at the agent's own.
- **The thread says when an agent goes.** One that exits on its own, one that can't start, and one a restart stopped each leave a line in the thread saying so.
- **The coordinator and reviewers only read** (ADR-004). They read throwaway copies: the coordinator, worktrees refreshed from the default branch each turn; a reviewer, a snapshot of the lead's worktree committed when its round begins (recorded in `workspace_snapshots`). Their agents' sandboxes are read-only where that still lets them call Althar's tools (Codex's `read-only`; Claude Code with edits denied and every command asking). Althar's reader rules are the backstop: reads, searches and fetches, and commands that only look, each with the flags it may take; anything else is refused with a reason, and nothing asks the person.
- **Agents report through Althar's tools.** The runtime serves an MCP server on 127.0.0.1 and gives each session a token for its role: the coordinator drafts and plans tasks, a lead says its step is done with `finish_step`, a reviewer reports with `report_review`. The token stops working when the session ends. What a step reports is a thread item the person reads instead of the whole turn.
- **A step that doesn't report needs the person** (05). A step's agent that ends its turn without calling its tool is reminded once; after that, and at once when its agent goes, can't start, refuses, or a restart stopped the step, the attempt waits on the person with a `stuck` call. One cut off at its own limit on a turn carries on a few times first. They tell the agent what to do, hand the step to another agent, or abandon it (a review is gone on without). A step that reports after all withdraws its call. Review that runs out of rounds with settled changes it hasn't seen needs the person too, rather than calling the task ready.
- **Issue drafts wait on the person, with no clock** (`IssueDrafts.ts`, 06). The coordinator's `draft_issue`, and a task's lead's (with its card in the task's thread, the task in Needs you while one waits, and the lead told its key once filed), records a draft and posts its card; only the person files it (`leadsNeedTheCard`). Filing marks it as being filed in the transaction that checks it is still open, then asks the tracker outside any transaction, so two presses file once; a tracker that may have taken the draft without Althar hearing so (no answer, an unreadable one, or Althar closed in the middle) leaves it uncertain, with a word to look on the tracker first, and it is never filed again unasked. The card's item carries the draft as it is, rewritten with each change.
- **A task's issue moves to In Progress as its first step starts** (`Issues.started`, 06). Not as its plan is proposed: `Runs` calls it once the first step has begun, and it runs in the background, so nothing it meets holds up or fails the task. It reads the issue as it is now, leaves one already started, done or cancelled as it is, and moves it once per issue: a fact (`external_link.issue_started` or `external_link.issue_start_failed`) says it was tried, and a later start doesn't try again. The move is an outward action, recorded with its receipt. A move or a failure leaves one quiet notice in the task's thread, and the coordinator hears of it in its news and in `read_task`. Off where the project's rules say (`moveIssues`, on by default); trackers with no In Progress of their own are skipped without a word.
- **Plans start on the runtime's clock.** A mini task's plan starts at once, with no countdown (`start_task`). A proposed plan starts after its countdown (25 seconds) whether or not a window is open, unless the person holds it. A plan that came due while Althar was closed is held at launch, not started unannounced. Starting is idempotent: a plan runs once.
- **A task's course is the person's** (`Tasks.ts`, 05 "Task and run lifecycle"). What applies where a task stands is worked out once, for the window's menu and for the commands; one that no longer applies does nothing. Stopping suspends the run in one transaction (its attempts cancelled and marked stopped, its run attempt interrupted, a stuck call withdrawn) before every agent on the task stops, so no step takes an agent going as one that went. Resuming runs the run again on a new run attempt, from the step stopping cut short (`Runs.resume`), on its last lead or the agent the person picked; what the person said meanwhile is the lead's first word. Abandoning declines a waiting plan, withdraws the task's calls and suspends its run, then stops its agents; its worktree and branch stay. Reopening is only for an abandoned task, never a merged one: it puts back a worktree whose folder went, from its branch, and opens the task where it was, a run cut short still suspended, a plan that never started proposed again, held. A task's commands run one at a time, through stopping and starting its agents, and a session being stopped is never carried on with. What may write to a run is fenced by its run attempt, checked in the writing transaction: nothing new is admitted on a suspended run or for whatever read it before it was resumed, a step's report from before a stop and resume is dropped and recorded (`node_attempt.report_dropped`), and an attempt whose agent was starting as the task stopped doesn't run: that agent is stopped once it is up. Publishing is admitted and started in one transaction. An abandoned task has no agent started or handed to on it until it is reopened, and abandoning declines a plan accepted but not yet run. Publishing in flight as the task stops says what it did on the host when it ends, and neither ends the run nor opens a call; nothing ends a suspended run, and no step of one asks the person anything. An abandoned task whose pull requests merge on the host after all is done, and a plan accepted as its task was abandoned gets no run.
- **A run is the task workflow, on the kernel's tables.** A started plan becomes a run with its attempt, execution and graph revision; each step is a node (the review and settling rounds by iteration) with its node attempts. The lead's session carries Implement and settling; a reviewer runs in a step thread of its own. Another round of review runs only if settling changed the worktree (its tree id, untracked files included) and rounds are left.
- **A usage limit moves the work on, or waits for the reset,** as the project's rules say (05; move on by default). An agent is out from the turn that reached its limit until the reset its error gave, or for an hour without one. Moving on, the next free agent takes the work over from a brief: signed in on a plan (an agent paid per use, on a key, is never moved to unasked), not out, in the agents' order, and not the run's other step's agent unless nothing else is free, when the thread says it reviews its own work. Its model is the plan's for it, else the last it ran in the project, else its own. A step runs again on it as when the person hands it over, held meanwhile so nothing said before it is told counts. Waiting, a step is held until the reset and then runs again on the same agent; with no reset known, it needs the person, whose call offers handing it on or trying it again, never telling it anything. A planned agent already out is passed over as a step starts. What the person said in the turn that failed goes to whoever carries on, with word that it may have been acted on, and with the brief if the agent never read it; the coordinator and a lead outside a step move on or wait the same way. What waits for a reset comes back at it, after a restart too. The thread says it in one line.
- **An agent's sign-ins are accounts, each in a home** (ADR-012, `Accounts.ts`). Its usual folder is its first account, made the first time the agent is asked for; an account Althar adds gets a folder of its own, named by its id so it never moves, with what of the usual folder isn't the account's own linked in (again as each session starts), never a sign-in, and removing it signs it out with the agent's own tool and deletes the folder; one another tool made is adopted as it is, found by its folder's name, never opened. A session starts with its account's home in the agent's environment and records the account. Sign-ins and usage limits are per account, and an agent is out only when all its accounts are. A session takes the thread's own account while it can, else the first, in the person's order, that isn't signed out or out. Moving on from a usage limit tries the same agent's next account, on the same model, before another agent, only where the project's rules turned rotation on (off by default), and only among the accounts the project allows; a live session whose account is out isn't carried on with.
- **A project's rules are revisions** (`Policies.ts`, ADR-013): the mode, the always-ask, never and always-allowed lists, command rules, the ending, the usage-limit rule and accounts. A change is a new revision, recorded as a fact by whoever made it, and a run cites the revision it started under. A change that replaces a list can name the revision it was made against, and is refused where the rules have moved on since; an allow rule for words the rules ask about or never allow is refused, so it never takes their place. Permissions decide with the rules as they are at the request; the MVP's worded first revisions read as every kind asking.
- **Allow rules come after what always asks** (`rules.ts`, ADR-018). What always asks (a kind on the list, or a command the project asks about) is held for the person whatever the allow rules say; what would otherwise ask is let through where an exact rule matches the line, or each command that would ask starts as an allow rule says or is of kinds always allowed, with commands that only change folder or look riding along (a redirect on one is a write); a line whose commands only show when it runs never is. The decision keeps the rules that answered and their revision, and the thread's tool call says the first. A judge (DEV-22) would answer after the allow rules and before the person, only what isn't held.
- **An always answer keeps what the call offered** (`Permissions.ts`). As a call opens, the runtime works out what an always would keep and, by trying each, the scopes Allow always and Deny always would hold by; the call carries them, an answer names a scope, and the runtime keeps that rule (an allow rule, or the never list) with the answer, as the person's revision, after trying it again against the rules as they are then, and refuses a scope that wouldn't hold. Then, and whenever the rules screen changes the rules, every call still waiting in the project is decided again, and one the rules no longer keep for the person is answered by them; a call made while the rules changed is decided again as it starts to wait.
- **Each ask the rules make has a kind** (`rules.ts`), or is one they can't tell, and a request is every kind it is: Never refuses any of them. With everything allowed, what the rules can't read is refused while Never lists anything. Command rules match each command of a line as the shell would run it, and as what a package runner or interpreter runs for it, the program by name, `*` for anything; deploying is read in a command's program or subcommand, never its arguments.
- **A task's ending is worked out once, when its plan is made** (`Changes.endFor`): the plan's own, else the project's, else a draft where the host is connected; no known host, its branch.
- **A task ends where its host lets it.** A plan made while the host wasn't connected opens its pull request after all if the host is connected by the time the work is done; otherwise the task ends on its branch, and its thread says why and what to do. The person opens its pull request later, as a draft, once the host is connected (`OpenChange`), from the task or the dock.
- **A task's repositories without a pull request merge here** (`localMerge.ts`, `Changes.mergeHere`, 06). Every one is planned first with `git merge-tree`, so nothing moves unless all of them can: no conflicts, the commits the person saw still on the branch, and, where a working tree has the default branch checked out, nothing uncommitted there and no untracked file where the merge puts one. Then each default branch moves, refs first (`update-ref` from where it was) and checkouts last (`merge --ff-only`); one that still refuses puts back what moved. Nothing is pushed. The task settles once every repository is merged, its pull request or here (`settleIfDone`).
- **After its first push, a task's branch is pushed by the person** (06). The lead commits; a task's open pull request says how many commits on the branch here aren't on it yet (`unpushedOf`, against the pull request's head, else the commit Althar last pushed), and `Changes.push` pushes up to the commit the person saw. The lead has no tool to push; it asks the person to with `push_to_pull_request`, a `push_request` item in the task's thread with the commits that would go up, from what the pull request has to the branch's head, and the head Push sends. What it has is the latest of what is known of it that the worktree knows, never an older commit behind it: the remote's branch as the remote says now, else the host's head, the commit Althar last pushed, and the head as last seen. It is refused, in words the lead acts on, without a pull request or its host, when the pull request isn't open, when nothing is new (naming what isn't committed), when the branch no longer has what went up, and when the remote has commits the worktree doesn't. Asked again with more, the newer takes the older's place. A push that reaches its head marks it pushed and tells the lead; a push refused because the branch moved (`ChangedSinceSeen`) shows the branch as it is now on it, or why that can't go up (`blocked`); the pull request merging or closing closes it.
- **A card's phase puts what waits on the person, and work under way, before ready:** a task sent back after its run passed is running while its lead works on the note, and ready again when it's done. Settled cards are worked out once.
- **The home is one read across projects** (`Queries.home`): every live project with its ink and when it last had work, each open task that runs, waits on the person or is ready, as its card, every open call, and what the loop did since a moment: steps' results, the usage limits and quiet steps it dealt with (the notices it marks `about`), and the permission asks the rules answered, counted. The moment is the window's, else when the person last left the home on this device (`devices.home_looked_at`), else a day ago. Nothing the person did is there.
- **A project changes after it is made** (`Projects.ts`, 01): renamed (its slug, and so its worktrees' folders, stays), drawn in another ink, its repositories added, left out (`detached_at`; tasks keep theirs, and the last one stays) or given a role, and removed (`archived_at`). Each is recorded as a fact of the project, so clients read it again. Removing declines its proposed plans, withdraws its calls and cancels its runs in one transaction, then stops every agent on it, so no step reacts to an agent going; after it, no plan starts, no agent starts and nothing is said to one there. Its folders, worktrees and branches stay. Tasks and the coordinator are told each repository's role.
- **A fork's pull requests open where its project says** (`Changes.ts`, `forks.ts`). Its branch is pushed to the fork; its pull request opens on the fork, as before, or on the repository it was forked from, from the fork's branch (each connector's `from`). More commits go to the fork too. A task made for the repository it came from starts from that repository's default branch (fetched from `upstream`), and its pull request targets it.
- **A project's ink is chosen once, when it is made**: the one the person chose as they named it, or the first, from where its id points, that no live project has (`inkFor`, in the contracts, so the window shows the same pick first). It is kept, so the mark stays the one the person learnt, until the person picks another (`SetProjectInk`), which may be one another project has.
- **A task's search row is written where what it is found by is** (`Search.ts`, 02 "Queries"). Its title, what the person asked, its lead's summaries and what it built, its pull requests' and issue's keys, its branches, and the files its agents' tool calls changed are one row of text, which SQLite's FTS5 index reads. `indexTask` writes it from the store in the transaction that changes any of them (making or renaming the task, the person writing to it, a step reporting, linking a pull request, an issue or a new branch), and writes nothing where it holds the same already; a write that changes one of those somewhere new calls it too. The files stand as of the lead's last report. Search never reads git.
- **Cards are read, not written.** A task's card in the coordinator's thread holds only the task's id; what it shows is read from the task, its plan, its run and its sessions. Touching the item tells watching clients to read it again. Every task gets one, whoever started it.
- **Services capture what they need.** Each service's methods return effects with no requirements, so the adapter can call `Permissions.decide` from its own fibers.

## Checks

- `bun run check`: format, type-aware lint and type checks.
- `bun run test:coverage`: the runtime against in-memory and temporary databases, temporary git repositories and the scripted fake agent, in process and as a process; gated at 90% of lines and branches.

## Gaps

- **The workflow is fixed.** Every run is Implement then Review; a running plan doesn't change, and the graph is never patched. Controller generations are always 1 and not yet fenced; after a restart, a step that was running needs the person rather than picking up on its own.
- **Running turns are watched, not only ended ones** (`Stalls.ts`, the reckoning in `stallWatch.ts`, 05). A turn shows life by its agent's updates and, while one of its tools runs, its process tree's CPU (`processTree.ts`, one `ps` listing a look); waiting on the person and the machine sleeping don't count. A stall climbs a ladder: carry on, start afresh, ask the person, and the agent is stopped. A loop, told by a call's command or whole input, is told once to try another way; a step's work is held to a budget since the person last spoke; either way only the turn stops, and the session keeps its context. Each rung says so in the thread, and asking the person on a step is a `stuck` call with what was tried.
- **Stopping never waits on an agent for ever.** One that doesn't end its turn within the grace is stopped with its process, and its turn recorded as cut short.
- **A review copy leaves out ignored files,** such as `node_modules`, since it is the worktree's tree; a reviewer can't run tests that need what the lead installed.
- **Findings are settled by the lead alone.** The person sees them but doesn't answer them yet.
- **Permission judgments are opt-in.** The coordinator answers permission requests in its mode; conversational questions from leads still need the person.
- **No timeout per step yet.** A step whose agent keeps working without end isn't stopped; the MVP plan's budget per node will bound it.
- **Session commands have no receipts in the store.** A retry within a launch gets the first one's result; across a restart, the session is gone anyway.
- **Rules read commands, not what they do.** A script that writes outside the worktree isn't caught by the rules; the agents' sandboxes are the boundary (Codex's and Claude's). OpenCode has no sandbox yet.
- **Briefs are text in the first prompt,** not artifacts.
- **Nothing in the artifact store is swept yet.** Files whose rows went, and old pictures and output, stay until mark-and-sweep from the references is built (07); retention per kind is an open question.
- **Sessions are not loaded after a restart;** a lost session stays lost, and the person starts a new one.
- **Raw protocol capture** is not written to its bounded file yet.
- **Questions are answered where they were asked only.** The home, the edge and the board list them and take the person to the task, or the coordinator's conversation; none answers in place, by choice: the home stays calm.
