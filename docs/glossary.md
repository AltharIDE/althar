# Glossary

The words Althar's interface uses, with the word the architecture docs use
for the same thing. The interface says the left column. Code, docs and ADRs may
say the right. When something new needs a name on screen, add it here first.

## Where work happens

| On screen | In the model | What it is |
|---|---|---|
| Project | `Project` | A body of work with its own rules, knowledge and history. It may have no repositories. |
| Repository | `RepositoryBinding` | A repository that the project's tasks may change, with its role. It is shared by everyone on the project. |
| On this Mac, Map it later | `RepositoryLocation`, or none | Where this device keeps that repository. "Map it later" is a binding with no location here. On the Sources view that state is "needs mapping". |
| Reading it | read-only inspection | What Althar does to a folder before a project exists. It changes nothing. |
| Role | `RepositoryBinding.role` | What a repository is to its project: Service, Frontend, Infrastructure, Library, Docs or Other. Suggested from its name, changed in the project's settings; tasks and the coordinator are told it. |
| Leave out | `RepositoryBinding.detached_at` | Taking a repository out of a project: new tasks can't change it and the coordinator stops reading it. Tasks made with it keep it. Nothing in its folder changes. Not "remove" or "detach". |
| Where tasks open pull requests | `RepositoryBinding.change_target` | For a fork (an `upstream` remote beside `origin`): on the repository it was forked from, or on the fork. The branch is pushed to the fork either way. |
| Colour | `Project.ink` | The ink a project's mark is drawn in: one of eight, picked for it when it is made, changed under "Name and colour" in its settings. Never "ink" on screen. |
| Remove from Althar | `Project.archived_at` | Taking a project out of the window and the home. Its agents stop and nothing it planned starts. Its folders, its tasks' worktrees and their branches stay. Opening its folder again makes a new project. Not "delete" or "archive". |
| Remove finished tasks' folders | `folder_wait` in `settings` (`FolderCleanup.ts`, ADR-056) | In Settings › Work on this computer: when a finished task's folder goes. Smart, to start: a review's right away, a merged change's after 3 days, a done task's after a week, an abandoned one's after 2 weeks, sooner when the disk runs low; or after a day, a week or a month; or Only when I clean up. Its branch stays, and the folder comes back when the task needs it. Not "worktree" on screen. |
| Clean up | `CleanUpFolders` | Removes every finished task's folder nothing holds back, whatever its wait. It asks nothing first: nothing it takes is lost for good. |
| Held back | a folder's hold (`FolderHold`) | A finished task's folder Althar won't remove by itself: changes not committed, a change's commits pushed nowhere, something running from it, opened today, or git can't read it. Listed apart, each with why, and removed only by hand with Remove, which says first what goes with it. |
| Folder removed, Folder back from its branch | workspace state `cleaned`, a notice with `role: 'folder'` | The lines across a task's thread as its folder goes and comes back. While it comes back and is set up again, the task's chip says Bringing its folder back. |
| Agent | runtime, adapter | Claude Code, Codex, GitHub Copilot, OpenCode and the like, as installed on this machine. |
| Account | `AgentAccount`, its home | One sign-in of an agent, kept in a folder of its own. The agent's usual sign-in is its first account; the person can add more, or bring in folders a switcher made. Named by the person ("work"), it shows after the agent's name: "Codex (work)". |
| Signed in as | `ProviderPrincipal` | Who the agent says you are, for an account. The agent keeps its own sign-in; Althar never holds the credential. |
| Sign in | vendor login, `auth_required` | Opens the agent's own sign-in, for an account. |
| Out of usage | usage limit (`usage_limit`) | The account has used its allowance until a reset. Depending on the project rules, the task is Paused, moves to another of the agent's accounts, then to another agent, or waits on the person, who moves it to a model that is free or waits for the reset. A call for it has the kind Out of usage. |
| Waiting for the connection | a step held for `agent_unavailable`, after a `transient` failure (ADR-060) | The step lost its connection, offline or its agent's service out of reach: the task is Paused, and carries on by itself once the computer is back and the service answers. While the service answers with errors, it says when it tries again instead; after a few tries, Stuck. Not Stuck, and no reminder is spent. |
| Offline | the app's reading of the network, `Connectivity` | One word in the window's bar while the computer is offline. Work under way carries on once it is back; new work waits rather than start. |
| Try again | the person's answer `retry`, on the agent the step was on; `TryAgain` in a chat | On every Stuck call: runs the step's turn again in the session it was in. First where the connection or the session failed. A review's is Review again. Under a coordinator's turn that ended in an error, it sends what the person said again. |

## Who does the work

| On screen | In the model | What it is |
|---|---|---|
| Coordinator | coordinator | The project's agent in the Talk room. It plans tasks and hands them out, but writes no code itself. |
| Task | `Task` | One piece of work with an outcome, usually one change. |
| Change, Review (a card's kind) | a task's kind, `TaskCard.kind`, read from what it has and never stored (DEV-96) | The word after where a task stands on its card and in its row. Review: it reads someone else's pull request, with nothing of its own. A plain task has no word: a quick task the coordinator starts at once (a question, a prototype, a release from this Mac), whose plan stays on this Mac, whatever its lead wrote. Change: every other task, every planned one among them, a quick task the person had made one, and any task with a pull request. A task only moves toward Change, when the person says so: they ask a quick task's lead to make it a change. |
| This task's work is on a branch of its own now, …, which stays on this Mac | `workspace.branched` from no branch (`firstWrite.ts`, ADR-035), a notice with `role: 'aside'` (ADR-042) | A line inside the lead's work in a quick task's thread, as its lead first changes the repository: Althar made the task's branch there, with that work on it, so nothing is lost, in the same folder with the same lead. The task stays plain, and nothing of it is pushed or opens a pull request. What its lead throws away in its scratch folder, and pictures it hands back, don't count. |
| This task is a change now: reviewed by …, it opens a draft pull request when it's done | `make_it_a_change`, the lead's tool (`task.made_change`, ADR-035), a notice with `role: 'aside'` (ADR-042) | A line inside the lead's work in a quick task's thread, once the person asked its lead to make it a real thing: its new title, the reviewer it named (or "with no review"), and how it ends (a draft pull request, one ready for review, or, where its repository is on no host Althar knows, on its branch), with the branch its work is on under it. The lead's next report goes through the review, then the pull request opens. |
| Lead | the task's primary agent (the docs sometimes say worker) | The agent that owns a task: it implements, runs the steps and answers them. Never "worker" on screen. |
| Step | workflow node | One stage of a task: Implement, Review, Verify. Steps report back to the lead. |
| Steps, the plan | workflow graph | A task's steps before it starts (the plan) and while it runs. |
| Graph | a task's runs, their nodes and tries (`ThreadSnapshot.task.graph`, the kit's `StepGraph`, ADR-054) | A task's face beside Conversation and Outputs (g): what it went through, a lane for each agent and model, its steps as cards in the order they ran, and a marker where each round of work starts (You asked, You followed up, From the coordinator). A card opens its report; a step that needs you is answered there. Not "graph" for the plan, which is its steps. |
| Tried three ways | run attempts, the repair ladder | What Althar already did before asking you: a retry, a repair, another agent. |

## You and the work

| On screen | In the model | What it is |
|---|---|---|
| Call | attention request | Something only a person can decide. Violet. |
| Needs you | attention requests addressed to you, and tasks ready to accept | The board lane, the count at the top of a project's screen, and the violet number on a project's tab (the home's tab counts every project). A task waiting on a call shows in it once, as its own card saying the call's kind and why; a call no task waits on, such as the coordinator's question, is a card of its own. One rule says which tasks are ready for you (`needsYou`, `shared/calls.ts`): every ready task, so a change to accept (its checks passed or failed, or with commits to push), commits after its last pull request to open a new one for, a review drafted, a Finished task, and work handed back. The board, the home (its list, its count and each project's line), the edge and the tabs all use it. A task Kept for later is not in the lane, and no count includes it. |
| Tab | a project the window keeps open | One per project the person keeps open, at the top of the window, after the home's. It goes back to where in the project they last were. ⌘1 is the home, ⌘2 onwards the projects. |
| Round the notch, In the menu bar | the edge (`main/edge.ts`) | Where Althar shows what needs you while you're in another app: an island round the notch on a Mac that has one, which is the notch alone until something needs you, or Althar's mark in the menu bar, with a dot while something needs you. Either opens to what needs you, where a permission is answered in place, with the work in progress counted in one line under it. Settings calls it "In other apps" and shows it on every system: off a Mac with a notch it is the menu bar, the system tray, or, on a desktop with no tray, only Althar's window, and there is nothing to choose. |
| Permission | permission attention request | A call asking whether an agent may do something, such as run a command or change a file. Allow it once or always, or don't: with what to do instead, or never (on the edge, once or not). Several at once stack, with Allow all. |
| Allowed, Denied; Once, Always, Never | a permission answered on the home or the edge | An answered permission's line, which stays where it was, at its height, quiet, until you leave: its kind says Allowed or Denied, and where its answers were it says what you said (Once, Always or Never), then where an always or a never was kept ("kept in meridian's rules"), your note when you denied with one, or else which project it was in. |
| Question, Needs your answer | question attention request | A call where an agent asks the person to choose: one or more questions, each with its options, each option with what it means, and room for your own words. Answered in the task, where it was asked. The home and the edge list it calmly, by what it asks and why, in what the agent said just before (or else who asks, and where), and Answer takes you to it, its first choice in hand; the board's card shows its options' names. Answered, it folds to what you said; withdrawn, it says "Not answered" and why. |
| Stuck | attention request at the end of the repair ladder | A task that can't finish without you. There is no Failed status. |
| Ready to accept | task phase `ready` | Work that is done and waits for you to accept it. |
| Finished | a plain task's phase `ready` | A task that isn't a change (a prototype, a spike, a quick task) whose lead is done. It waits in Needs you, counted, with the pictures or files it handed back, small, or else its branch, until you settle it with Done or Keep for later, in its card's corner on hover (a check and a pin) or in its header inside the chip that says where it stands, or tell its lead (`settle_task`). Opening it moves nothing. A review whose review was posted, written to again and answered with nothing new to post, is Finished too. |
| Done | a plain task, or a review answered, the person settled (`task.done`, `marked: true`) | A Finished task you settled: what it left running, such as a page, stops, and it moves to Settled; where something wouldn't stop, it stays, and says so, for you to try again. Writing to its lead later opens it again as a follow-up, which ends in Needs you. |
| Kept for later | phase `kept` (`tasks.kept_at`) | A Finished task, or a drafted review, you took out of Needs you as it is, its page still up. Settled's head names it beside Settled (Kept 3); pressed, Kept shows in Settled's place, a line each, with Done on hover. Writing to its lead brings it back, and what the lead does next ends in Needs you. |
| Queue, "Enter queues it; the lead reads it next" | `after_current` | What you write while the lead works. It waits for the lead's current turn to end. |
| Send now | `interrupt_and_continue` | Stops the lead's turn to read your message, then it carries on with both. |
| Interrupt the lead | turn interrupt | The composer's square. Ends the lead's turn; the task stays open. The line in the thread reads "Interrupted by you". |
| Listening to | `external_links.listening` | In the chip over a task's composer: the pull requests Althar asks for news while it runs, what they last said, and, for a moment, what just came. Stop stops it: nothing said there after reaches the thread or the lead. |
| Running, Ran | what an agent left running (`LeftRunning`, ADR-022), and Althar's own runs (`Launches`, ADR-023) | In the chip over a task's composer, with why it waits and what it listens to: commands its lead sent to the background, such as a dev server, and what Althar runs of the task itself; over the coordinator's, in a pill of its own, every run Althar has going in the project, each saying where it runs. Each with where it answers, which opens in your browser. Stop stops one. One that ended by itself says how ("exited 1") until you clear it; in the task's chip, only one that failed is named, and those that finished well fold away in its list, or, with nothing else to show, are a quiet count that opens them. What a lead left runs as long as its session does; Althar's runs until you stop it or quit. |
| Run card | a `run` thread item (`RunCard`, ADR-023) | What a run of the project leaves in the thread it was asked for in: where it runs, the command, where it answers, as a link, and how long it has been up, with Stop. It stays once the run is over, saying how it ended, with Run again. |
| Installing dependencies in meridian…, Installed dependencies in meridian | a `setup` thread item (`Setups.ts`, ADR-023) | A line across a task's thread: Althar setting up the task's worktree before its lead starts, with the install its lockfile names, or "Setting up meridian…" with the setup kept for it. Once it went through, the line goes, and it is a line inside the lead's first round's work (ADR-042). Failed, the end of what it printed stands under it, and the lead is told. Not "bootstrap" or "provision". |
| Worked 12m · edited 3 files, ran 6 commands; Working · 2m | a round's work (`rounds.ts`, `WorkLine`, ADR-042) | One faint line in a task's thread for all the work of a round, between what its lead says first and what it says last: how long, and what it did, counted. It opens to every step in order, what the lead said on the way among them and the pictures it looked at, small. While the lead works, it says what it is on, in the lead's own last words. A round that said nothing is the line alone, after who worked. Not "turn", "trace" or "log" on screen. |
| From the coordinator | a notice with `role: 'relayed'`, written as the lead receives it (ADR-042) | What the coordinator passed on to a task's lead, on the person's side of its thread, where the lead read it: what it is in a line ("One more round"), three lines of the rest, and Show all, with Althar's mark printed faint in its corner. The round it starts follows it. |
| What it checked, Not checked | a lead's report's `evidence` and `unverified`, under its result (`Checked`, ADR-042) | Under what a lead says when it hands its work in, after its screenshots: what it checked other than by looking, a line each, ticked or crossed, opening to what it printed; and what it couldn't check, still the person's. Its screenshots stand above, large, in the groups their names make. |
| It also retook A2 and B5, shown earlier | a later report's screenshot named as an earlier one (`Gallery`, ADR-042) | A line under a lead's screenshots naming views it showed before and took again, each opening full size on a click, so the same view isn't shown twice. |
| Althar (a line in a task's thread) | a runtime notice with no role (ADR-042) | Althar saying something the person should know, by name, in one line: a conflict with the default branch and that it asked the lead to settle it, checks that failed, a pull request opened, a conflict now the person's (its name warm). A list of files is said as how many. |
| Asks you to push | a `push_request` thread item (`PushRequest`) | The lead asking you to push what it committed to the task's pull request, in the task's thread: the commits that would go up, with Push. Nothing goes up until you press it, and then only what it shows. It stays once pushed, asked again or closed. |
| Run `bun run dev`, Run Public site; Everything to run | `RunProject`, a project's `runnables` (ADR-023, ADR-044) | The split Run button at the top of the project's front and in a task's bar. One press runs what the project runs by default, the first of its list, with no agent: on the project, in a copy of its default branch; on a task, in its worktree. Its chevron lists everything it runs, the running ones first, checked: pick one to start or stop it, several at once. Then Add something to run… and Edit the list…. |
| Something to run, What althar runs | a runnable (`runnables`, ADR-044) | One of what a project runs: a name, where someone gave one, and a command, in one of its repositories. Its repository's own way to run has no command of its own: it is worked out from the repository, or kept by an agent. Added three ways: typing its command, from package.json, or by asking the coordinator. Edit the list orders them (the first is the default), edits and removes them. |
| Find a task, ⌘K | `SearchTasks`, the coordinator's `find_tasks`, `task_search` (ADR-035) | Finding a task by what it was about: its title, what you asked, what its lead built, a pull request's number, a branch or a file. ⌘K in a project searches it; on the home, every project. With nothing typed it lists the tasks changed last ("Recent"); found, each says where it stands in a word and what matched besides its title. Not "search results" or "query" on screen. |
| Hold | plan held | On a plan waiting to start: its countdown stops, and it starts when you say. |
| Start now | plan accepted | Starts a plan waiting to start, from its card or the task menu. |
| Issue draft | an `issue_draft` thread item, `issue_drafts` | An issue the coordinator, or a task's lead, drafted on a connected tracker, as a card in the Talk room or the task's thread: the tracker, where it goes there, its title, description and labels. Nothing is filed until you file it. |
| File issue, File again, Edit, Discard | issue draft filed, changed, discarded | On an issue draft: File puts it on the tracker, and the card then shows its key as a link; Edit changes it first; Discard drops it, filing nothing. Not filed, the card says why, and File again tries again. Perhaps filed (its answer was lost), the card says it may be on the tracker already, to look there before File again. Never "create", "submit" or "approve" on screen. |
| Review, Review #123 | a review task: one with an external link of kind `review` and a workspace it only reads (`Reviews.ts`) | A task that reviews someone else's pull request, started by asking the coordinator or pasting the pull request's link and asking. Its lead reads a copy of the pull request's code that Althar fetched, runs nothing of it, and drafts a review. Not "audit" or "inspect" on screen. |
| Reads ninemate’s branch · runs nothing of it · no network · posts nothing until you do | what a review's lead can reach (`ReachLine`) | The sentence under a review's header; each phrase opens what it means. "No network" is there for a pull request from outside the team: from a fork, or by someone GitHub doesn't name one of the repository's people. "Posts once drafted" replaces the last phrase where the setting below posts it. |
| Review draft | a `review_draft` thread item, `review_drafts` | The review a lead drafted, as a card in the review's thread: the pull request, your verdict beside the lead's suggestion, its summary, and its comments on lines, each Kept or Dropped. Nothing is on GitHub until you post it. On a pull request from outside the team, Approve is never chosen for you. Waiting to be posted, its task says Review drafted: on its card in Needs you, on the home, the edge, in a notification and in its header. |
| Your verdict; Comment, Approve, Request changes | `ReviewVerdict` | What a review says of a pull request as a whole. The lead suggests one ("Claude Code suggests Request changes"); yours is what posts. |
| Post review, Post again, Edit, Discard | review draft posted, changed, discarded | On a review draft: Post review puts it on the pull request with your verdict and the comments kept, and the card folds to "Review posted on #123: Request changes, 2 comments", with Open on GitHub; the review is then settled. Edit rewords its summary and comments; Discard drops it, posting nothing. Not posted, the card says why, and Post again tries again. Perhaps posted (its answer was lost), the card says it may be on GitHub already, to look there first. Never "submit" or "approve" for Post on screen. |
| Post reviews of my team’s pull requests without asking | the `post_team_reviews` setting | In Settings, off by default: a review of a pull request by one of the repository's people, from a branch of its own, posts itself as soon as its lead drafts it. One from outside the team always waits for Post. |
| Stop the task | run suspended | From the task menu. Every agent on it stops, and the step it was on is cut short. Nothing runs, and nothing waits on you, until you resume it. Status: Stopped. |
| Resume | run resumed | From the task menu, or by writing to a stopped task: the lead carries on the step it was on, with what you wrote first. |
| Abandon, a merged task | commits after its last pull request left out (`leaveOut`, `refs/althar/left-out/…`, ADR-034) | From the task menu, while commits after a merged task's last pull request are in none yet and its lead isn't in a turn: they are what keep it in Needs you. It settles without them, done still, at the time it first settled where it had one; an open task merged in every repository too, as settling it asks. They stay on its branch and in its worktree; only what is committed after counts again. Never marked `abandoned`: its change is in. |
| Abandon | task abandoned, its run suspended | From the task menu, asked first. Ends the task without its change. It moves to Settled. Its worktree and branch stay. |
| Reopen | an abandoned task open again | Only for an abandoned task, never a merged one. It opens on the same worktree and branch, where it was: a step cut short resumes, work that had passed is ready again. Writing to an abandoned task reopens it too. |
| Follow-up, Following up | a round of work after the plan (a run with no plan, ADR-034) | What the person asks a task's lead for once its plan's steps are done: the task runs again, ready, merged or settled as it was, and its track names its first step Follow-up, its header Following up. The lead finishes it with its summary, a review follows where the plan has one, and one that changed nothing leaves the task where it was. Not "round" or "iteration" on screen. |
| Attach a pull request… | `AttachPullRequest`, the coordinator's `attach_pull_request` (ADR-052) | In a task's menu: the task follows an open pull request it didn't open, by its link or number, such as one upstream from the fork. What people say on it and its checks come to the task, and its work goes to that pull request's branch, with no new one. Where the task's branch isn't based on its head, it asks first: Start from its head keeps the task's own commits on top. Not "link" or "connect" a pull request on screen. |
| Skip the review | a run's review step skipped | In a task's menu while its work still has a review to come or under way: it is ready once its lead is done, unreviewed this time. The next follow-up has its review again. |
| Open a new pull request, Before this | a task's next pull request (ADR-034) | Offered once a task's pull request merged or closed and its lead committed more after it: a new draft, on a new branch from the default branch, with only the commits after the last. The task shows its latest pull request, and each earlier one under it as "Before this: PR #1, merged on GitHub." |
| Althar restarted | reconciliation after process loss | Not said in threads: a lead that stopped with Althar starts again when the person next writes to it, and nothing it was doing runs twice. A step that was running carries on by itself, with a line in its thread; it asks the person only if its lead can't start, or a restart stops it again soon after the last one carried it on. |

A call's kind reads the same everywhere it shows: on the board, in the bar's preview and on the home.

## Automations

| On screen | In the model | What it is |
|---|---|---|
| Automations | `Room.Automations`, `automations` (ADR-061) | A project's view between Board and Settings: the work that starts by itself on a schedule, on this computer while Althar is open, as cards, the one that paused itself first, with a violet dot on the view's name. A card opens its automation's own page there. |
| Automation | an automation and its definitions | A kept request and a schedule: what each run is asked, its lead, what it ends in (nothing outside this computer, a draft or ready pull request, or a review of each new pull request), when it runs (days at a time where the computer is, or every hour), and its limits. Made by asking the coordinator, on its card, or with New automation. |
| Run, Runs, Run now | an automation's occurrence, and the task it started | One time an automation ran, or didn't: made something, nothing to do, failed, missed while the computer slept, or skipped and why. Its page lists them, its card shows the last seven as marks. The one place "run" is said on screen. Run now runs it once, with every limit a run has. |
| Try it once now | `RunAutomationNow` on a proposed automation | On an automation not turned on yet: one run as it would run. |
| Turn on, Off until you turn it on | `TurnOnAutomation`, an automation `proposed` | Nothing of an automation runs until the person turns it on. A change the coordinator makes that reaches further than before puts it back to waiting for them. |
| Paused, Paused itself | `paused_by` the person, or itself | The switch on its page pauses it; nothing of it starts until it is on again, and a run under way finishes. After three failures in a row it pauses itself and says why, violet. |
| Pause all automations | the `automations_paused` setting | In Settings and the Automations view's menu: nothing of any automation starts until they are resumed; runs under way finish. |
| Post this automation's reviews from now on | `posts_reviews` | On an automation's first review draft, beside Post: posts it, and lets its next reviews post themselves; on its page, a switch. A pull request from outside the team always waits. |
| Open Althar at login | the desktop's `openAtLogin` preference | Offered on the Automations view while it is off, and in Settings: Althar opens with no window when the computer starts, so automations run after a restart. |
| From Althar's morning review | a review or pull request signed with the automation's name | How what an automation's run posts on the code host is signed, by the automation and the agent that wrote it. |

## Updates

| On screen | In the model | What it is |
|---|---|---|
| This update couldn’t move your data | a migration that didn't finish (`MigrationFailed`, `ForeignKeyViolations`), or the copy before it (`BackupFailed`) | What the window shows instead of opening when an update couldn't bring the person's data to its new shape. It says the data is safe, where the copy from before the update is, and what stopped it. Nothing of Althar runs behind it. |
| Copy from before the update | a backup, in the profile's `backups` folder | The copy of the person's data Althar makes before an update moves it, kept as a file they can find. The newest three are kept. |

## When something goes wrong with Althar

| On screen | In the model | What it is |
|---|---|---|
| Report a problem | a problem report, sent to the reports Worker, which makes a Linear issue | From Help in the app's menu on a Mac, the foot of the quick settings, or About Althar in Settings: a dialog with one box, "What happened?". The screenshot of the window and the logs go with it unless the person switches them off; "See what's sent" lists every item; an email if they'd like a reply. Without the reports service, it is saved in Downloads and a mail opens to send it with. |
| Report this | a problem report about something that went wrong, carrying its task, or what stopped an update | Quiet, at the end of a Stuck call's answers, and on This update couldn’t move your data. It opens Report a problem about that step or that update. On a Stuck call it answers nothing: the step still waits. |
| Logs | `main.log`, `runtime.log`, `agents.log` | What the app writes as it runs, in the system's place for logs. A report sends the last part of each, with paths in the home folder and repository names hidden. |
| Install id | usage data's random id, kept in the profile's `desktop.json` | Which install a report came from, and nothing about who. The same id usage data and crash reports send, whether or not they are on. |
| Crash reports | `$exception` events to PostHog's error tracking, from the main process (`crashReports.ts`) | What failed in Althar and where in its code, sent without anyone writing in, masked as a report is: never anyone's code, what is written, or any name. A switch of its own beside Usage data in About Althar, and one quiet line with the same switch on the first screen. A native crash's minidump stays on the computer; only that it happened is sent. |

## What comes back

| On screen | In the model | What it is |
|---|---|---|
